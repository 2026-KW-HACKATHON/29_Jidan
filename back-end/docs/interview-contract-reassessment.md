# 제공된 인터뷰 계약에 대한 재평가

> 아래는 HEAD `49f6712` 당시의 역사적 평가다. 이후 승인된 구현·복구·최종 검증은 [원자 작업 계획과 실행 기록](interview-structured-output-atomic-tasks.md)을 따른다.

기존 계획은 프론트 F 범위만 고쳐서 재개할 수 없다.
기존 AI 내부 구조를 보존하면서 기능을 확장하는 접근 자체가 이번 요청의 기준에 맞지 않았다.
사용자가 제공한 출력·흐름·API·ERD를 기준으로 구현을 평가해야 하는데,
계획은 기존 내부 모델과 추가 저장 설계를 기준으로 요구를 다시 나누고 결정했다.
AI를 다시 작성할 수 있다는 사용자 지시 아래에서 기존 내부 구조의 유지는 의무가 아니다.

이 문서는 적합성 평가이며 새로운 대응표, 흐름, 타입 또는 구현 작업 목록이 아니다.
코드 삭제·수정, 구현 재개, 테스트 실행, Git·PR 상태 변경은 수행하지 않는다.
평가 기준 체크아웃은 `interview-structured-output-20261008`, HEAD는 `49f6712`다.
기존 구현과 이번 변경을 구분하는 기준 커밋은 `d35c26d`다.
별도 `interview-state-174`의 0044는 현재 HEAD에 통합되지 않은 안으로 구분한다.
아래 경로는 별도 표기가 없으면 `back-end/` 기준이다.

## 제공된 계약은 무엇을 이미 정했는가

원본 `docs/지단manual_architecture.md:5`는 AI의 질문·카드 유형·내용 생성과 서버의 검증·저장·진행을 정한다.
같은 문서 `:11–18`은 질문, 평가, 요약, 사진 추천, 정정, 초안 생성의 책임을 구분한다.
처리 상태·오류·revision·게시 여부는 AI 출력이 아니며 녹음 시간과 파일 선택은 프론트 책임이다.
이 책임 분담을 새로운 내부 상태 모델을 설계할 근거로 확대할 수 없다.

원본 `:25–46`의 `QuestionOutput`과 `QuestionCard`는 질문과 안내 카드의 출력 필드를 제공한다.
`:55–59`, `:91–104`는 새 항목 ID 부여, 기존 ID 유지, 읽기 전용 상태와 카드 유형의 의미를 정한다.
답변 제출 자체가 `COMPLETED`를 뜻하지 않으며 일반 예시는 실제 매장 업무가 아니다.
질문 출력의 두 카드 유형과 요약 뒤 사진 추천을 분리하는 것 역시 이미 제공된 조건이다.

원본 `:111–139`는 `AnswerEvaluation`과 `ReviewOutput`을 제공한다.
`summary`, `structure.shifts`, `structure.sections`, `structure.missing_information`이 명시되어 있다.
`Shift`, `Section`, `MissingInformation`은 기존 콘텐츠 구조를 재사용하라고 명시되어 있다.
이 내용을 구현하는 것은 정당하지만 별도의 중간 콘텐츠 계약을 보존할 의무는 여기서 나오지 않는다.

원본 `:153–206`의 `PhotoSuggestionOutput`은 저장된 요약·섹션을 입력으로 받는다.
`suggestions`와 `sectionId`, `title`, `items`, `footer`가 이미 주어져 있다.
서버의 대상 검증, ID 부여, 기존 `PHOTO_SUGGESTIONS` 및 `attachmentTarget` 연결도 명시되어 있다.
추천 없음·대상 없음·추천 실패가 필수 인터뷰 진행을 막지 않는다는 조건도 제공되어 있다.

`openapi.yaml:18778–18803`은 `ManualGuidanceCard`와 `ManualInterviewQuestion.guidanceCards`를 정의한다.
`openapi.yaml:18681–18714`의 `ManualGuidancePhotoTarget`에는 `intentId`, `target`, `sectionId`가 있다.
`openapi.yaml:18866–18905`의 `ManualInterviewReview`에는 요약·근무조·섹션·사진·미확정 정보가 있다.
따라서 공개 필드와 대상 관계가 없어서 새 매핑이 필요하다는 진단은 맞지 않는다.

`docs/erd/manual.md:253`은 `ready_content`와 마지막 성공 콘텐츠 보존을 정한다.
같은 문서 `:268`은 API `ManualInterviewReview` 내용과 사진의 보존 및 생성 시 ID 유지를 정한다.
`:270`은 선택된 검토 revision·내용·사진·미확정 정보의 불변 생성 입력을 정한다.
`:287`은 사진의 이름·설명·순서를 보존하고 같은 섹션 ID의 초안 첨부로 이어받도록 정한다.
이 연결은 이미 제공된 계약이며 물리 컬럼의 유무와 별개다.

## 문서의 시점과 승인된 한정 조건

`d35c26d`의 `docs/manual-interview-design.md:3`은 구현 전 계약과 구현 완료를 구분한다.
같은 기준 문서 `:143`은 오래된 ERD 문구보다 최신 사용자 정정이 우선한다고 명시한다.
자료의 표현이 다른 부분을 모두 동시에 충족하는 새 흐름으로 합성해서는 안 된다.
`docs/erd/ai-interview-flow.md:28–36`의 depth·재시도·실패 보존도 기존 실행 조건이다.

기준 문서 `:193–209`에는 카드 의미·ID·첨부 대상·답변 처리 중 불변 질문 스냅샷이 이미 있다.
현재 `docs/manual-interview-design.md:212` 이후는 이번 작업에서 추가한 A01 설명이다.
이를 사용자가 처음 제공한 요구의 독립 근거로 역인용하지 않는다.

사용자가 선택한 “실제 다음 미답변 질문이 있을 때만 추천, 마지막 인텐트는 수동 첨부”는 유지한다.
이 한정 자체를 구현 버그나 미해결 계약 부족으로 판정하지 않는다.
다만 이 선택은 원본 전체 추천 흐름의 구현 완료를 증명하지 않는다.
추천을 위한 내부 task·revision·저장 설계가 적합한지도 별도로 평가해야 한다.

## 기존 AI 모델과 이번 구현의 판정

`RawStructure`, `StructureSnapshot`, `new-N` 참조는 이번에 처음 만든 것이 아니다.
`d35c26d`의 `app/ai/schemas.py:60`, `:160`과 `app/ai/contracts.py:93`에서 이미 확인된다.
이를 이번 신규 발명으로 비판하면 변경의 출처를 잘못 설명하게 된다.
그러나 기존에 있었다는 사실은 제공된 계약보다 우선하거나 반드시 유지해야 한다는 근거가 아니다.

제공된 `QuestionOutput`, `QuestionCard`, `ReviewOutput`, `PhotoSuggestionOutput`의 구현은 정당하다.
판정 대상은 그와 별개인 중간 모델·임시 참조 규칙을 독립 계약처럼 보존·확장하는 접근이다.
계획 `docs/interview-structured-output-atomic-tasks.md:65`, `:139`는 기존 구조 보존을 조건으로 둔다.
이 조건의 정당화는 부족하며, AI 재작성 가능성을 막는 기준으로 사용할 수 없다.
`app/interview/content.py:14–34`, `:42–64`의 기존 변환과 사진 재연결은 재사용 후보다.
재사용 판단은 파일이나 타입의 존속 자체가 아니라 제공된 ID·내용·사진 보존 조건으로 해야 한다.

## 저장 요구와 물리 설계의 판정

계획 A01/A02(`docs/interview-structured-output-atomic-tasks.md:103–118`)는 제공된 관계를 다시 결정 대상으로 놓았다.
기존 계약의 해석 확인과 실제 구현 대조는 필요하지만 새 관계를 만드는 작업과 구분해야 한다.
계획 B05/B06(`:169–184`) 및 D02(`:263–269`)는 특정 저장 형태와 migration을 먼저 정했다.
이는 계약상 저장 요구와 특정 물리 구현의 필요성을 혼동한 접근이다.

현재 `migrations/versions/0042_interview_question_guidance.py:18–20`은 질문 안내 열을 추가한다.
`migrations/versions/0043_interview_evaluation_aspects.py:15–16`은 `missing_aspects` 열을 추가한다.
별도 state 워크트리의 `0044_interview_photo_suggestions.py:25–30`은 추천 JSON·revision·task·attempt를 추가한다.
0044는 현재 통합 코드의 사실이나 완료 근거가 아니라 미통합 물리 설계안이다.
이 변경들은 기존 ERD/API 대응에 비추어 다시 평가할 대상이며 확정된 선행 조건이 아니다.
모든 추가 열이 불필요하다고 단정하지 않으며, 열이 없다는 이유로 계약이 빠졌다고도 판단하지 않는다.
이 문서는 새로운 열·migration·저장 모델을 제안하지 않는다.

## 정정과 카드 의미의 판정

원본 `docs/지단manual_architecture.md:218–222`는 정정 시 ID·사진 보존과 임의 사진 이동 금지를 정한다.
기준 `docs/manual-interview-design.md:179`, `:185`도 모호한 정정과 명시적 삭제를 구분한다.
현재 `app/ai/validation.py:289–320`은 유한한 한국어 정규식과 전체 발화 일치로 삭제를 허용한다.
이 허용 문구 목록은 제공된 보존 요구 자체가 아니라 구현이 추가한 제품 제약이다.
허용 문구 밖의 정상적인 음성 삭제 정정까지 거절하는 정책은 교체·재작성 후보로 판정한다.
ID 누락이나 모호한 결과로 기존 사진을 잃지 않게 하는 보호 요구는 그대로 유효하다.

카드 UUID 형식·중복·허용 ID 검사는 참조 안전성의 일부를 확인한다.
그 검사만으로 실제 답변에 근거한 업무인지, 충분한 내용이 확보되어 `COMPLETED`인지 입증되지 않는다.
표현·순서가 바뀐 같은 업무를 동일하게 식별하는지 역시 UUID 검사와 다른 평가 대상이다.
원본 `:102–104`와 `openapi.yaml:18801–18803`의 의미 조건을 만족했다는 별도 근거가 필요하다.

## 검증 증거와 프론트 범위

fake/scripted AI를 이용한 실제 HTTP·독립 DB 회귀는 저장·재조회·실패 보존의 검증 자산으로 재사용할 수 있다.
다만 새 schema·migration·정규식 정책의 자기일관성 테스트 통과는 설계 적합성을 증명하지 않는다.
그 테스트가 통과해도 실제 AI의 업무 구분·충분성·정정 이해·사진 추천 품질은 미검증일 수 있다.
기준 `docs/manual-interview-design.md:132–134`, `:159`도 정적 계약 검증과 실제 구현 검증을 구분한다.
이번 평가는 새 테스트를 실행하지 않았으며 기존 통과 기록의 의미를 확대하지 않는다.

기존 프론트는 수정하지 않은 상태를 기준으로 확인하며 신규 프론트 구현은 범위 밖이다.
프론트 PR #175도 이번 평가에서 변경·종료·병합하거나 선행 의존성으로 삼지 않는다.
프론트 범위만 고친 계획은 내부 AI 구조를 기준으로 삼은 문제를 해결하지 못한다.

재사용 후보는 제공된 계약을 실제로 지키는 기존 변환·보존 로직과 회귀 검증이다.
교체·재작성 후보는 독립 계약처럼 굳어진 중간 표현과 추가된 정정 문구 제한이다.
특정 저장 설계의 필수성은 정당화가 부족하고, 현재 테스트는 입증한 범위 안에서만 유효하다.
다음 판단의 기준은 새로운 설계자료 작성이 아니라 이미 제공된 계약에 AI 실행을 맞추는 것이다.
