# 점주 매뉴얼 작성 MVP 구현 계획

점주는 음성으로 답하고, AI가 정리한 매뉴얼을 확인하며, 틀린 내용은 다시 말해서 고친다. 전사 원문 확인·텍스트 답변·직접 구조 편집·사진 이름과 설명 편집은 MVP에 포함하지 않는다. [OpenAPI 0.10.0](../openapi.yaml)과 [인터뷰 계약](manual-interview-design.md)을 기준으로 API 응답을 재사용 컴포넌트에 연결한다. 이 문서는 프론트 구현 계획이며 API·AI·STT의 구현 완료를 뜻하지 않는다.

## 사용자 흐름

1. 선택한 매장의 작성 상태를 조회하여 시작하거나 이어 쓴다.
2. 질문을 보고 말한다. ‘답변 마치기’를 누르면 앱이 업로드 → 전사 READY 조회 → VOICE 답변 제출을 이어서 수행한다. 전사 원문을 표시하거나 별도 제출 확인을 받지 않는다.
3. 완료된 주제의 요약을 확인한다. ‘수정할게요’를 누르고 “A가 아니라 B야”처럼 말하면 해당 인텐트의 요약을 정정한다. 기본 질문·추가 질문은 각각 자신의 questionId에 답하고 다음 질문과 depth는 서버가 결정한다.
4. 필요하면 사진을 올려 현재 근무 구조·업무에 연결한다. 사진 없이 계속할 수 있다. 기본 이름은 앱이 최초 연결 시 부여하고 caption은 null로 보낸다. 이후 재조회·재시도·순서 변경 시 저장된 이름을 유지한다.
5. 모든 인텐트가 끝나고 검토가 READY이면 completion으로 초안을 생성하여 최종 검토에 진입한다.
6. 최종 검토에서도 ‘수정할게요’로 음성 정정한다. 항목에서 시작하면 SHIFT/SECTION ID, 전체 수정이면 MANUAL 대상을 전달한다. 생성된 초안은 draft/corrections로 고치며 완료된 인터뷰를 다시 열지 않는다.
7. 서버에 저장된 초안으로 근무자 화면을 미리 본다. 부족 항목을 명시적으로 확인하고 현재 versionId·revision으로 게시한다. 성공 응답 후 완료 상태로 이동한다.

실제 근무자의 매뉴얼 탐색·AI 질의응답은 이 구현 범위 밖이다. API의 TEXT 입력·전체 내용 편집·사진 메타데이터 수정 기능은 유지하되 MVP 화면에 노출하지 않는다.

## 기존 Figma와 컴포넌트 사용

[녹음 중](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=376-1676), [답변 처리 중](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=376-1711), [음성 정정](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=346-1422), [사진 첨부](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=777-2979), [최종 검토](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=330-2757), [미리보기](https://www.figma.com/design/ZaFHresnBXJ1h98Xl1AUDj?node-id=777-3203)를 재사용한다. Figma 보강은 구현 선행 조건이 아니다. 남아 있는 텍스트 입력 오류 컴포넌트와 사진 설명 입력은 MVP에서 사용하지 않는다.

기존 MobileLayout·AppBar·Button·Modal·디자인 토큰을 재사용한다. 질문 패널, 안내 카드, 진행 목록, 근무 구조·업무 섹션, 사진, 부족 항목, 처리 상태를 표시 컴포넌트로 분리한다. ManualVoiceComposer는 답변·인텐트 정정·초안 정정에서 녹음 동작을 공유한다. 표시 컴포넌트는 props와 이벤트만 사용하고 API 호출·전환은 상위 흐름이 담당한다. 최종 검토와 미리보기는 같은 ManualContent 렌더러를 사용한다.

질문별 안내 카드 등 현재 계약에 없는 presentation 정보는 API 응답에 있는 필드만 우선 사용한다. 질문 문자열을 분석하여 화면 종류를 추측하거나 예시 목록·선택지를 API의 필수 선행 작업으로 추가하지 않는다. 목록 수와 미리보기 페이지 수는 실제 응답에서 계산한다.

## 상태와 실패 복구

- 세션·인텐트 검토·초안·전사·초안 정정 작업의 ID와 revision을 각각 관리한다. 로컬에는 녹음 Blob·녹음 상태·선택 위치만 보관하고 브라우저 영구 저장을 추가하지 않는다.
- 녹음 취소·화면 이탈 시 마이크와 타이머를 해제한다. 권한 거부·미지원은 안내하며, 무음·전사 실패는 재녹음 또는 전사 재시도를 제공한다. 텍스트 대체 입력은 없다.
- 인텐트 요약은 확인하거나 건너뛸 수 있고 이전 요약에 재진입할 수 있다. 정정과 사진 변경은 선택한 intentId에 귀속하며 현재 질문 답변을 덮어쓰지 않는다. 요약 실패는 해당 검토에서 복구한다.
- 초안 정정은 RUNNING/SUCCEEDED/ERROR로 조회한다. 처리 중에도 마지막 내용을 보여주되 정정 중임을 표시하고 편집·게시·초안 교체를 막는다. 성공하면 초안을 다시 조회한다.
- 실패하면 기존 내용을 보존한다. 모호한 정정은 다시 말하도록 안내하고, 재시도 가능한 오류는 보존된 입력으로 재시도한다. 실패 안내 후 기존 내용을 명시적으로 검토하면 그대로 게시할 수 있다.
- ManualService와 HTTP 어댑터를 분리하고 #123의 인증·HTTP 인터페이스를 따른다. 세션 쿠키·CSRF·AbortSignal·멱등 키를 사용하고 응답 경계에서 필수 필드와 상태를 검사한다.
- 비동기 작업은 기본 2초와 Retry-After를 따르고 비활성 화면에서는 조회를 중단한다. 복귀 시 최신 상태를 확인한다. 응답 유실은 같은 본문·키로 복구하며 작업 지연만으로 다시 제출하지 않는다.
- 충돌 시 기존 입력을 다른 초안 ID나 새 revision에 자동 적용하지 않는다. 늦은 응답·다른 매장 전환·중복 클릭을 분리해 처리한다.

## 구현 순서

| 작업 | 구현 내용 |
| --- | --- |
| #31 입력 기반 | 시작·이어하기, 공통 표시 컴포넌트, 녹음·취소·업로드·전사·자동 답변 제출, 서비스 어댑터 |
| #32 인터뷰와 요약 | 응답 기반 질문·진행, 주제별 요약·음성 정정·확인·건너뛰기·재진입·복구 |
| #34 사진 관리 | 사진 선택·업로드·기본 이름 부여·연결·순서·연결 해제, 이름·설명 편집 제외 |
| #33 최종 검토와 게시 | 초안 생성·음성 정정·부족 항목 확인·근무자 미리보기·게시 |

업로드와 연결 저장은 구분하고 연결 저장 실패 시 같은 파일로 복구한다. 연결 전 사진은 로컬 Blob, 연결 후에는 보호 조회 API로 표시한다. 삭제는 연결부터 해제하며 다른 참조가 있는 파일을 지우지 않는다.

검수는 기존 /__preview의 매뉴얼 그룹과 /__manual 진입으로 제공한다. 매장 ID와 복귀 경로를 전달하며 실제 인증 연결은 #123에 맞춘다. 계약 모의 응답과 HTTP 어댑터를 먼저 검증하고 실제 인증·AI·STT·스토리지 통합은 #131에서 수행한다. 운영 화면에서 실제 실패를 모의 성공으로 바꾸지 않는다.

## 검증과 완료 기준

- 음성 완료 후 전사 원문 확인 없이 답변·정정이 한 번만 제출되는지 검증한다.
- 녹음 권한 거부·미지원·취소·이탈·무음·전사 실패·자원 해제와 음성 20 MiB·120초, 사진 10 MiB 경계를 검증한다.
- 기본 질문·추가 질문·depth 5 부족·다음 인텐트·최종 생성과 요약 독립 실패를 검증한다.
- 초안 정정 실패의 내용 보존, 모호한 정정 재입력, 오래된 작업·revision·초안 교체, 처리 중 게시 차단, 성공 후 부족 항목 확인 초기화를 검증한다.
- 사진 기본 이름과 null 설명, 재시도 시 이름 보존, 파일 공유·연결 해제·업로드 후 연결 저장 실패를 검증한다.
- 401·승인 대기·CSRF·422·409·429와 알 수 없는 오류, 중복 요청·응답 유실·늦은 응답·다른 매장 전환을 검증한다.
- 프론트 lint·test:ci·build와 미리보기/운영 빌드 분리를 검증한다. 최대 너비 390px·본문 스크롤·하단 액션을 유지하고 Figma와 인앱 미리보기를 수동 비교한다. 브라우저 자동화는 추가하지 않는다.

독립적으로 검증·리뷰·revert 가능한 단위마다 즉시 커밋하고 테스트를 함께 포함한다. PR은 해당 영역 dev를 대상으로 작성한다. 필수 CI를 모두 통과하면 별도 리뷰 승인을 기다리지 않고 merge commit으로 병합한다. 테스트하지 않은 실제 AI·STT·DB 경쟁을 검증 완료로 기록하지 않는다.
